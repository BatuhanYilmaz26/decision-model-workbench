# Train a D3 model on a cloud GPU

[Provider directory](README.md) · [D3 family and native data](../models/d3-family.md) · [Project overview](../../README.md)

Train a pinned D3 variant on AWS, Azure, GCP, Modal or RunPod when your computer cannot run
its native training profile. Use the same reviewed domain data and frozen study
across providers. The returned model must pass independent evaluation in its
serving environment before an owner can release it.

The selected D3 backend adapts the original FP32 answer-code readout while freezing
the pinned BF16 backbone. It preserves complete soft targets and the native
prompt, option and code order. This is the workbench's adaptation method;
the publisher's Transformers wrapper is inference-only. Each variant uses its own pinned identity and geometry in the
[family guide](../models/d3-family.md). See the [Edge model source](https://huggingface.co/vllm-sr/d3-edge/tree/c454ee39b862248d70abd7f84195d2f54ffe6d43)
and [shared training contract](../models/d3-family.md).

## Prepare your domain data

Start the [local application](../../README.md#run-on-your-computer). Describe your
decision and the data you need, define the allowed outcomes, then enter or upload
examples using the [CSV, XLSX, TSV, JSON or JSONL contract](../import-guide.md).
Review labels before training. Optional [synthetic generation](../synthetic-generation-guide.md)
uses a separate generative teacher; D3 itself scores allowed answers and does not
write training examples.

Reserve independent real validation, calibration and test records. Synthetic
candidates can extend training after review and must not replace those holdouts.
At least eight calibration records are required, but that floor does not establish
representative domain quality. Save your release criteria before preparing a job.
The [retrieval-evidence examples](../../examples/d3/README.md) illustrate the schema
and are insufficient for operational training by themselves.

## Build a pinned training image

Use a Linux/amd64 Docker builder, enough storage for dependencies, the selected base
checkpoint (1.19 GB to 52.18 GB) and retained exports, and the same repository source as the application.
The [D3 Dockerfile](../../docker/models/Dockerfile.d3) installs the separate
[D3 runtime](../../requirements/d3-native.txt), caches the exact public checkpoint
and disables subsequent Hub downloads. Domain records and provider credentials
must stay outside the image. Review the checkpoint's license before redistribution.

From the repository root:

```bash
docker build --platform linux/amd64 -f docker/models/Dockerfile.d3 --build-arg D3_PROFILE=d3-edge -t decision-d3-edge .
docker run --rm decision-d3-edge python -c "print(open('/app/d3-image.json').read())"
docker run --rm --gpus all --network none decision-d3-edge python -c "import torch; assert torch.cuda.is_available(); print(torch.cuda.get_device_name())"
```

Choose `D3_PROFILE=d3-lite`, `d3-nano`, `d3-mini`, `d3-flash` or `d3` for another
variant, with a distinct image tag/digest and enough build storage for its weights.
Each image caches one selected checkpoint. The image uses Torch 2.10 / torchvision 0.25 CUDA 12.6 wheels and Transformers
5.17 with the eager native kernels. [PyTorch's installation instructions](https://pytorch.org/get-started/previous-versions/)
describe the matching wheels. Do not combine this environment with the Liquid
5.19 profile or assume optimized FLA, ROCm or vLLM support. Larger inputs/batches
need additional memory beyond the model's startup threshold.

Push the image to a registry accessible to your provider. Record its immutable
`registry/repository@sha256:...` digest and `/app/d3-image.json` source fingerprint.
The image and the application must agree on the source, backend and checkpoint.
The Linux GPU image recipe is experimental: validate the built image on your
chosen GPU/provider before committing domain data or paid compute. Local contract
tests do not establish provider account access, image execution or billing.

## Configure your provider

Use your own provider credentials in the server/operator environment described
by the selected guide. They are cloud-compute credentials, not a D3 model API key.
Keep credentials out of domain data, image layers, browser fields and Git.

| Provider | Configure and operate the job | Profile template |
|---|---|---|
| AWS | [Managed SageMaker AI](../managed-cloud-training.md), [direct training API](aws.md) | [AWS](../../examples/cloud/aws-profiles.json) |
| Azure | [Managed Azure ML](../managed-azure-training.md), [command jobs](azure.md) | [Azure](../../examples/cloud/azure-profiles.json) |
| GCP | [Managed custom training](../managed-gcp-training.md), [custom job API](gcp.md) | [GCP](../../examples/cloud/gcp-profiles.json) |
| Modal | [Managed GPU Sandbox](../managed-modal-training.md), [GPU/Volume SDK](modal.md) | [Modal](../../examples/cloud/modal-profiles.json) |
| RunPod | [Managed GPU Pod](../managed-runpod-training.md), [Pod and SSH setup](runpod.md) | [RunPod](../../examples/cloud/runpod-profiles.json) |

Copy the selected provider template to a private configuration file. Set its
account, region, identity, storage, GPU, resource limits and image digest as the
guide requires. Set `source_sha256` to the fingerprint from your built image and
declare only its selected backend, for example `"training_backends": ["d3-edge"]`. An image built for a different D3 variant, Liquid or Laya must not be
declared compatible with the selected backend. Set `DMT_CLOUD_PROFILES_FILE` to that private file and
restart the services. The application exposes only profiles allowed for your tenant.

Set `max_artifact_bytes` high enough for the full frozen weights, readout,
tokenizers and native/canonical/lineage data. The approved cap can be up to 64 GiB.
A 32 GiB cap cannot hold the largest D3 export. The controller refuses a declared
cap smaller than its weights/readout before creating a run, and reserves three
times the approved artifact cap plus 1 GiB locally for download, extraction and
admission. A 64 GiB cap therefore needs at least 193 GiB free at retrieval, in
addition to already retained data. The trainer uses one CUDA device; a multi-GPU instance may incur charges for
additional unused GPUs. Provision the admission host for the model's
[RAM/VRAM floors](../models/d3-family.md#choose-a-variant-and-provision-its-resources).
Artifact transfer/extraction deadlines scale with the bounded size; allow training,
packaging and transfer time in the provider's runtime/cost budget.

## Submit, retrieve and release

1. In the project, select the desired **D3 variant (native readout, text/JSON)**
   and **Cloud GPU**.
   Cloud preparation does not need a local GPU or installed D3 model environment.
   The cloud profile uses CUDA and disables checkpoint downloads.
2. Select the approved provider, region, GPU and immutable image digest. Confirm
   that the provider may receive the domain data and prepare the remote study.
   This freezes source, model, four data roles, settings and release policy;
   preparation itself does not allocate paid resources.
3. Choose the matching managed provider profile. Approve both data transfer and
   paid compute, then submit. Use the provider guide to monitor or stop the run.
   Reconcile a lost/uncertain submission before trying another allocation.
4. Retrieve the completed full export. Managed retrieval checks the artifact and
   queues independent admission. For an operated host, follow the
   [manual admission workflow](../remote-admission-guide.md).
5. Configure `DMT_D3_PYTHON` in the admission/serving service to a compatible D3
   environment. Admission measures the original validation, calibration and test
   roles, reloads a second time and retains the fitted temperatures. Supplied
   remote metrics do not determine the local release decision.
6. Inspect the recomputed metrics and your saved release gates. Activate an eligible
   model with a reason, then use **Make decision** or the
   [application API](../product-workflow.md#6-release-and-integrate). Retain an
   eligible prior version for rollback.

Cloud exports record CUDA as their calibrated device. Admission and serving need
the compatible GPU profile; renting a training GPU does not make its export fit
an underpowered local computer. You can operate the application/model service on
a suitable GPU host. Changing the serving device requires target-profile evaluation;
matching selected answers alone does not establish probability/calibration parity.

## Run on an operated GPU host

Download the frozen study as `data/d3-study.zip` and retain its archive/request
SHA-256 values. In the matching model environment, set `DMT_D3_CACHE` to the
pre-cached checkpoint directory, `DMT_CLOUD_IMAGE_BACKEND=d3-edge`,
`HF_HUB_OFFLINE=1` and `TRANSFORMERS_OFFLINE=1`. Set `ARCHIVE_SHA256` and
`REQUEST_SHA256` to the values from the approved study.

Validate without training:

```bash
python -m decision_workbench.training.cloud_runner --archive data/d3-study.zip --archive-sha256 "$ARCHIVE_SHA256" --request-sha256 "$REQUEST_SHA256" --work data/d3-check --out data/d3-check-export --check-only
```

Use fresh work/output directories for training:

```bash
python -m decision_workbench.training.cloud_runner --archive data/d3-study.zip --archive-sha256 "$ARCHIVE_SHA256" --request-sha256 "$REQUEST_SHA256" --work data/d3-train --out data/d3-export
```

The launcher runs the unchanged native trainer before binding remote provenance.
It refuses changed inputs/settings and publishes the manifest last. Do not add
remote provenance to a standalone export manually. Return the complete bundle,
including reviewed native assets and lineage. Source/configuration hashes are
checked before native loading, and Python bytecode caches are rejected.
