# Train and use D3 Edge for your domain

[Model directory](README.md) · [All guides](../README.md) · [Project overview](../../README.md)

Prepare reviewed domain examples, adapt D3 Edge's original answer-code readout,
calibrate it on reserved real data and release it through the localhost application,
or use the complete exported model from Python or the command line. This profile supports text and JSON with choice, yes/no and
ordered-score questions.

The adapter pins `vllm-sr/d3-edge` revision
`c454ee39b862248d70abd7f84195d2f54ffe6d43`. Its frozen BF16 backbone retains
the publisher's noncausal full-attention layers, causal Gated DeltaNet layers,
left padding, prompt and code order. Only the original 255-code FP32 readout is
updated. This workbench adaptation method is separate from the publisher's
inference-only Transformers wrapper; ordinary chat SFT is not its training contract.

This is an experimental native-model profile with local application and command-line
workflows. For rented GPUs, use the [five-provider cloud workflow](../remote-training/d3.md). The other
D3 variants, media, ROCm fast paths, vLLM and Semantic Router Engine require separate
adapters and qualification. Its local workflow uses the shared
[data, review and release controls](../product-workflow.md).

## Install a separate environment

Install the repository's [local application](../../README.md#run-on-your-computer),
then create a Python 3.12 model environment. Keep it separate from other models.

Windows PowerShell, from the repository root:

```powershell
py -3.12 -m venv .venv-d3
.\.venv-d3\Scripts\python.exe -m pip install -r requirements/d3-edge.txt
.\.venv-d3\Scripts\python.exe -m pip check
.\.venv-d3\Scripts\Activate.ps1
```

Linux shell:

```bash
python3.12 -m venv .venv-d3
source .venv-d3/bin/activate
python -m pip install -r requirements/d3-edge.txt
python -m pip check
```

The commands below use that environment's `python`. If PowerShell blocks
activation, use `.\.venv-d3\Scripts\python.exe` instead of `python`.
For NVIDIA CUDA, install matching Torch 2.10.0 and torchvision 0.25.0 wheels using
[PyTorch's instructions](https://pytorch.org/get-started/previous-versions/)
before installing the profile. The runtime requires the compatible Transformers
5.17 stack. Optimized `flash-linear-attention` and `causal-conv1d` are optional
upstream accelerators and are not part of this eager-reference profile.

The base weights occupy about 1.19 GB; allow additional space for tokenizer assets,
datasets and each retained full export. Startup requires at least 2 GiB free CUDA
memory or 3 GiB available host RAM. These are refusal thresholds, not a guarantee
that a particular batch/context fits. CPU training is experimental and can be slow.
The adapter chooses CPU or CUDA; macOS/MPS and Linux GPU images need separate
qualification. No paid model API key is needed.

## Define the decision and collect examples

Use the [retrieval-evidence example](../../examples/d3/README.md) for a specification,
CSV layout and inference request. Replace its domain, outcomes and examples with
your own. Supply text or JSON evidence available at decision time; the model
should not receive information that appears only after the outcome.

The [guided intake](../product-workflow.md#1-describe-the-decision) lets you describe
your domain/data needs, define allowed outcomes and enter or upload examples.
The [import guide](../import-guide.md) covers CSV, XLSX, TSV, JSON and JSONL.
Use [reviewed synthetic candidates](../synthetic-generation-guide.md) to fill
training gaps with a separate generative teacher. For example, request missing,
irrelevant, contradictory and sufficient evidence for each approved outcome.
D3 scores allowed answers and does not generate candidate text. Keep real held-out
records and their relatives out of teacher inputs.

For a standalone study, follow the [canonical data contract](../data-guide.md).
Review/correct labels before setting `reviewed=true` in an owner-controlled file.
Prepare your own reviewed CSV and specification:

```bash
python -m decision_workbench.cli validate --input data/reviewed.csv --spec data/spec.json
python -m decision_workbench.cli prepare --input data/reviewed.csv --spec data/spec.json --out data/d3-study --split-strategy group-random
```

For operational studies, prefer the appropriate chronological or entity-separated
reservations and inspect actual group membership. The four required files are
`train.jsonl`, `validation.jsonl`, `calibration.jsonl` and `test.jsonl`.
They must be nonempty, reviewed and schema-consistent. Validation, calibration and
test must contain independent real records; at least eight calibration records
are required. This numerical floor does not establish representative domain quality.
The six pending example rows are format illustrations and cannot train a defensible model.

## Train and release in the app

Use the application environment from the [root quick start](../../README.md#run-on-your-computer)
to start the services. Set the model interpreter before startup; the application
and the D3 environment can use different Python versions.

PowerShell, from the repository root:

```powershell
$env:DMT_D3_PYTHON = (Resolve-Path .\.venv-d3\Scripts\python.exe).Path
.\.venv\Scripts\python.exe -m decision_workbench.platform.cli run
```

Linux shell:

```bash
export DMT_D3_PYTHON="$PWD/.venv-d3/bin/python"
.venv/bin/python -m decision_workbench.platform.cli run
```

You can also enter the D3 model interpreter under advanced local setup before
starting a personal workspace. Separate API and worker processes need the same
`DMT_D3_PYTHON` setting. Restart services after changing it. Optional `DMT_D3_CACHE`
selects the checkpoint cache; otherwise it lives under `model-cache/d3-hub`
beside the workspace. Neither a paid API key nor a pasted workspace credential
is needed for personal localhost use.

1. Create or open a domain project. Describe the policy and data you need, define
   the allowed outcomes, and upload or enter examples. Review each label.
2. Reserve independent real validation, calibration and test roles. Use at least
   eight calibration records and save your release criteria. Optional reviewed
   synthetic candidates can extend training while preserving those holdouts.
3. Select **D3 Edge (native readout, text/JSON)** under **Training backend**.
   Check the configured packages and choose automatic, CPU or CUDA compute.
   Enable the pinned checkpoint download only when the complete cache is absent.
4. Queue training. The worker freezes source, settings, data and release policy;
   an isolated model child owns the model resource. The readout is adapted and
   the complete export is independently reloaded, calibrated and evaluated before
   registration. Job status and private operator logs distinguish failures from success.
5. Inspect per-question metrics and your saved release gates. Activate an eligible
   version with a reason, then use **Make decision** or the
   [authenticated decision API](../product-workflow.md#6-release-and-integrate).
   Retained eligible versions can be reactivated for rollback.

New exports record the device used for calibration and evaluation. Default serving
retains that CPU/CUDA selection, including CPU on a computer with a visible GPU.
A CUDA-qualified export does not silently fall back to CPU. Re-evaluate on the
target profile before moving a workspace/model to another kind of device.
The loader executes hash-checked publisher source bytes directly; native exports
do not include or execute Python bytecode caches.

## Export native training data

The exporter expands each canonical record into one native decision per question.
It retains complete normalized soft targets, choice insertion order, false/true
order and zero-based score levels. Canonical bytes, source groups, review metadata,
gold labels and lineage remain separate from the native prompts. Reserved control
tokens, unsupported media and prompts over the chosen input budget are refused;
inputs are never silently truncated.

```bash
python -m decision_workbench.training.d3_data --data data/d3-study --out data/d3-native --cache data/model-cache/d3-hub --download --max-length 2048
```

This command downloads only pinned tokenizer/configuration/code/license assets,
not model weights. For data preparation alone, install
[`requirements/d3-data.txt`](../../requirements/d3-data.txt) in a separate CPU
environment. Subsequent cached runs can omit `--download`.

The output contains `canonical/`, `native/`, `lineage/` and a hash manifest.
Native JSONL includes `id`, `question_id`, `prompt`, `input_ids`, `option_keys` and
`target_probabilities`. You supply canonical labels; you do not need to write
the model's letter codes yourself.

## Train, calibrate and reload

Use the original four canonical files as the trainer input. Choose a new output
directory for every attempt:

```bash
python -m decision_workbench.training.d3_runner --data data/d3-study --out data/d3-run --cache data/model-cache/d3-hub --download --device auto --max-length 2048 --batch-size 1 --grad-accum 4 --epochs 1
```

Use `--device cpu` or `--device cuda` to select explicitly. The first run downloads
the exact public checkpoint. Omit `--download` for complete offline caches.
For a small mechanics check on fictional data, add `--max-steps 1`; a one-step run
does not establish model quality or an adequate training budget.

The trainer updates the native readout, verifies unchanged frozen parameters,
exports the complete backbone/readout, independently reloads it and checks prediction
equivalence. It fits per-question temperatures on real calibration records and
reports validation/calibration/test metrics separately. Inspect `report.json`,
`manifest.json`, `data/` and `checkpoint/`. Fitted temperatures remain under
`calibration`; calibration-set metrics use `calibration_metrics`.

Evaluate per-outcome errors, Brier/NLL/ECE, abstention coverage and your domain's
critical-error costs using the [evaluation guide](../evaluation-guide.md).
An export is not an automatically approved production release.

## Use the fine-tuned bundle

Create a request containing the trained model's exact `questions` and new `state`;
the [example request](../../examples/d3/request.json) illustrates the shape.
Read the questions from the exported metadata to preserve the choice-key order:

```python
import json
from pathlib import Path

metadata = json.loads(Path("data/d3-run/checkpoint/dmt_d3.json").read_text(encoding="utf-8"))
request = {"state": "Replace with new decision-time evidence", "questions": metadata["questions"]}
Path("data/request.json").write_text(json.dumps(request, ensure_ascii=False), encoding="utf-8")
```

Point `--model` to the bundle root, which contains `manifest.json`:

```bash
python -m decision_workbench.training.inference --backend d3-edge --model data/d3-run --request data/request.json
```

Python integration:

```python
import json
from decision_workbench.training.inference import predict_export

with open("data/request.json", encoding="utf-8") as stream:
    request = json.load(stream)
answers = predict_export(
    "data/d3-run", request["state"], request["questions"], backend="d3-edge"
)
print(answers)
```

The loader verifies the whole bundle and pinned native code before inference.
Keep the exported questions and temperature metadata with the weights. Loading
only the backbone or using upstream `AutoModel` alone omits the workbench's
per-question domain calibration. Each result includes normalized probabilities,
the selected answer, maximum-probability confidence and an abstention flag;
scores also include `expected_score`. This confidence differs from the publisher's
entropy-based confidence. Application code remains responsible for authorization,
fallback and any action taken from a decision.

For repeated serving, verify the bundle and retain one engine. New exports default
to their recorded calibration device. Legacy exports without that field choose
CUDA when available, otherwise CPU. For an explicit target-device evaluation:

```python
from pathlib import Path
from decision_workbench.training.artifacts import file_sha, verify_manifest
from decision_workbench.training.d3_runtime import D3Engine

bundle = Path("data/d3-run")
schema = request["questions"]
manifest = verify_manifest(bundle, file_sha(bundle / "manifest.json"), "d3-edge", schema)
engine = D3Engine(bundle / manifest["checkpoint"], device="cpu")
answers = engine.predict(request["state"], schema)
```

Changing device, kernels or precision can change probabilities even when the
selected answer stays the same. Do not assume CUDA-fitted calibration or reported
CUDA metrics carry over to CPU. Evaluate the original reserved roles on the
intended serving device before accepting a deployment; fit calibration with that
same device/profile when training a new study. For example, with the retained engine:

```python
from decision_workbench.training.contracts import load_splits
from decision_workbench.training.metrics import evaluate_predictions

roles, hashes = load_splits("data/d3-study")
predictions = [engine.predict(row["state"], schema) for row in roles["test"]]
print(evaluate_predictions(roles["test"], predictions, schema))
```

Keep the original data hashes and validate calibration and critical-error limits
as well as test accuracy. CPU training and cross-device domain quality remain
experimental. Application-managed D3 release uses the frozen local study;
admission of D3 exports from remote providers is unavailable.
An operated GPU host can use the same CLI/environment and reviewed inputs. Consult
the [five-provider directory](../remote-training/README.md) for provider setup,
storage and compute controls; those managed images/controllers do not yet declare
D3 compatibility. Cloud training and enterprise application hosting are distinct.
